## 1 引言

### 1.1 编写目的

本文档对"智慧校园食堂点餐系统"的开发全过程做系统性总结，说明项目做了什么、为什么这样做、如何设计实现、三名成员各自承担了什么工作、当前完成到什么程度以及还有哪些问题。它与《软件需求规格说明书》（做什么）、《系统设计文档》（怎么设计）、《系统操作手册》（怎么用）共同构成完整交付材料，其中本文承担"过程与实现总结"的角色，是答辩时说明工作量和分工的主要依据。

### 1.2 项目背景

校园食堂午餐高峰集中在 11:30–12:30，现场排队时间长、热门限量菜到档口才知道售罄、商家凭感觉备菜缺少数据支撑。同时，学生带餐回寝室存在真实需求，但校内配送缺少规范渠道。本系统以《Java 高级开发技术》课程大作业为载体，采用前后端分离架构，围绕"线上点餐 + 防超卖 + 校内配送 + 经营数据"构建一套可运行的完整系统。

### 1.3 文档范围

本文覆盖需求、设计、实现、分工、验证与总结六个方面；环境安装与连库细节见两篇环境文档，逐步操作见《系统操作手册》。

### 1.4 术语与缩略语

| 术语 | 含义 |
|---|---|
| 档口 | 食堂内独立经营单元，对应一个商家账号 |
| 限量菜 | `is_limited=1` 且 `daily_stock>0` 的菜品，售完即不可下单 |
| 取餐码 | 自取单生成的 4 位数字，当日同档口内唯一；配送单无取餐码 |
| 校园配送 | 勤工助学性质的校内配送，学生付 2 元跑腿费，配送员抢单送达后结算 |
| 原子拆单 | 跨档口购物车在单个事务内生成多笔子订单，全部成功或全部回滚 |
| 担保交易 | 跑腿费下单时冻结在平台，配送员确认送达后才入账 |
| RBAC | 基于角色的访问控制，五表模型 + 四角色 |
| 降级模式 | Redis 不可用时主流程照常、增强能力退化为数据库实现的运行方式 |

## 2 项目概述

### 2.1 项目简介

系统面向校园食堂场景，提供四端应用：

- **学生端**（`/student`）：菜品浏览、购物车、下单、取餐码与二维码、钱包、优惠券、评价、投诉、站内消息、AI 助手；
- **商家端**（`/merchant`）：本档口菜品管理、出餐看板核销、语音播报、销量统计、投诉回应；
- **校园配送端**（`/rider`）：跑腿大厅抢单、我的配送、标记送达；
- **管理端**（`/admin`）：用户管理、档口审核、配送调度、投诉裁定与超时升级、优惠券投放、操作日志、全局统计。

### 2.2 开发目标

1. 完成课程硬性技术要求：前后端分离、Vue、Spring Boot、MyBatis、Redis、slf4j、Spring Security、RBAC；
2. 实现一条完整可演示的业务主线，并具备可讲解的亮点技术；
3. 四角色权限严格隔离，关键操作留痕可审计；
4. Redis 不可用时主流程仍可用；
5. 形成需求、设计、操作三类文档与可复现的演示数据。

## 4 系统设计

### 4.1 总体架构

```
Vue 3 前端 ──axios /api──> Spring Security 过滤链 ──> Controller ──> Service ──> MyBatis Mapper ──> MySQL
                                                              ├─ Redis/Redisson（预减库存、ZSet 热销榜、抢单锁）
                                                              ├─ @OpLog AOP ──> sys_operation_log
                                                              └─ @Scheduled ──> 投诉超时扫描
前端 AI 助手 ──HTTPS──> DeepSeek API（Function Calling，无 Key 时本地兜底）
```

分层职责：前端只负责交互与展示；Controller 做参数校验与鉴权入口；Service 承载业务规则与状态机；Mapper 负责 SQL；Redis 作为增强器；异常由全局处理器转为统一返回体。

### 4.2 技术选型与课程要求对应

| 课程要求 | 选型 | 落地说明 |
|---|---|---|
| 前后端分离 | Vue 3 + Vite 5 / Spring Boot 2.7.18 | 独立工程，Vite 代理 `/api`，REST + JSON |
| Vue 框架 | Vue Router 4 + Pinia + Element Plus | 四角色布局路由、守卫、登录态持久化 |
| Spring Boot | 2.7.18 / Java 11 | 统一返回体、全局异常、分层结构 |
| MyBatis | mybatis-starter 2.3.1 + PageHelper | 18 个 Mapper 与 XML，条件更新与分页 |
| Redis | spring-data-redis + Redisson 3.23.5 | `RedisSupport` 软依赖封装，锁与榜单 |
| slf4j 日志 | Logback + AOP `@OpLog` | 文件日志 + 落库审计 |
| Spring Security | Security 5.7 + jjwt 0.11.5 | JWT 过滤器、四角色 URL 规则、401/403 |
| RBAC | 五表模型 + RIDER 角色 | 鉴权时实时查库，禁用与改角色即时生效 |

### 4.3 数据库设计

基础脚本 `schema.sql` 建 16 张表，三个补丁追加 4 张（`rider`、`sys_message`、`complaint`、`sys_operation_log`），合计 20 张，utf8mb4 / InnoDB，无物理外键，金额均为 DECIMAL。

| 分域 | 表 | 关键设计 |
|---|---|---|
| RBAC（5） | user、role、user_role、menu、role_menu | 四角色；ADMIN 12 个权限点、MERCHANT 6 个、学生/RIDER 0 个（登录即可） |
| 食堂域（4） | canteen、stall、dish_category、dish | `stall.status` 0停业/1营业/2待审核；`dish.is_limited`/`daily_stock`/`sale_count` |
| 交易域（4） | cart_item、order_info、order_item、wallet_record | 订单含取餐码、`batch_no`、`delivery_fee`、配送四列；明细存菜名与价格快照及 `limited` 标记；流水类型 1充值/2消费/3退款/4跑腿收入 |
| 营销反馈（3） | coupon、user_coupon、review | 满减券、领券记录、一单一菜品一次评价 |
| 补丁新增（4） | rider、sys_message、complaint、sys_operation_log | 配送员档案、站内消息、投诉工单与超时升级、AOP 日志 |

### 4.4 核心流程设计

| 流程 | 设计要点 |
|---|---|
| 三重防超卖 | Redis 预减库存（`dish:stock:*`）→ Redisson 菜品锁（`lock:dish:stock:*`，按 ID 升序获取）→ MySQL `WHERE daily_stock>=N` 条件更新，行数 0 即回滚；Redis 挂掉退化为纯条件更新 |
| 跨档口原子下单 | 前端按档口分组；后端聚合预减、统一取锁集合，单事务循环建子单并写同一 `batch_no`；多档口自动关闭优惠券 |
| 退款全量回滚 | 取消与投诉成立共用 `rollbackOrderEffects`：退余额、按 `user_coupon_id` 精确退券、按明细 `limited` 标记补库存、减销量、Redis 余量与榜单回滚 |
| 配送担保交易 | 下单收 2 元跑腿费；抢单用 `lock:delivery:grab:{orderId}` + 条件更新保证唯一赢家；配送员本人送达后写入 `type=4` 流水结算 |
| 投诉闭环 | 状态机 0待处理→1已回应→2已裁定；定时任务每 10 分钟扫描 24h 未回应工单，幂等升级并推送站内消息；管理员裁定可勾选退款 |
| AOP 操作日志 | 关键方法标注 `@OpLog`，环绕通知写文件日志并落库，日志异常被吞掉不影响业务；管理端提供筛选查询 |
| AI 助手 | DeepSeek `deepseek-chat` + 5 个工具函数两轮调用；回复中识别菜品名插入推荐卡片；无 Key 走本地关键词兜底 |
| 二维码核销 | 学生端生成 5 分钟动态码（载荷含订单号、取餐码、过期时间），商家扫码或手工输入后前端校验并调用核销接口 |

### 4.5 接口规范

REST 风格；统一返回体 `{code, message, data}`；分页返回 `PageResult`；401/403 返回 JSON；参数用 `@Validated` 校验。主要路径前缀：`/api/admin/**`（ADMIN）、`/api/merchant/**`（MERCHANT）、`/api/rider/**`（RIDER），其余登录即可。完整接口见 `/doc.html`。

### 5.4 技术难点与解决方案

| 难点 | 解决方案 |
|---|---|
| 高并发下限量菜超卖 | Redis 预减 + 分布式锁 + 数据库条件更新三重防护，失败逐级补偿 |
| 跨档口下单一致性 | 单事务批量建单 + 统一批次号 + 统一锁集合，任一失败全回滚 |
| 退款副作用遗漏 | 将余额、券、库存、销量、Redis 回滚集中到单一方法供取消与投诉复用 |
| 并发抢单唯一性 | Redisson 锁 + `WHERE delivery_status=0` 条件更新，失败提示"手慢了" |
| 跑腿费安全结算 | 下单冻结、送达才结算，券不抵扣跑腿费，投诉退款只退菜品部分 |
| Redis 不可用 | 软依赖封装：锁降级直接执行、库存走数据库条件更新、榜单走数据库排序 |
| AI 密钥与可用性 | 前端直连 DeepSeek，缺 Key 自动降级为本地关键词问答 |

### 7.3 已知缺陷与未完成项

| 级别 | 问题 | 影响 |
|---|---|---|
| 严重 | 批量下单未级联校验，负数量可使 `pay` 为负并反向加钱改库存 | 资损风险 |
| 严重 | JWT 过滤器不校验 `user.status`，禁用账号的旧 token 仍可用 | 越权风险 |
| 严重 | 投诉退款先加钱再标记，未检查影响行数 | 可能重复退款 |
| 主要 | 二维码仅前端校验，后端核销不验码与时间 | 可伪造核销 |
| 主要 | 跑腿费结算路径不统一，管理员送达不结算，投诉退款不退已结算费用 | 账目不一致 |
| 主要 | 取消未分配配送单后仍留在待分配列表 | 调度异常 |
| 主要 | 无自动化测试、无压测报告 | 防超卖等指标缺少证据 |
| 一般 | 管理端送达按钮被置空、日志筛选值与落库值不符、`/student/dining` 为占位页 | 体验与完整性 |
| 一般 | JWT 密钥与数据库密码硬编码，AI Key 位于前端 | 生产环境风险 |

## 8 总结与展望

### 8.1 完成情况总结

按原 27 项任务口径统计：伍梦圆完成 10.5/11，开璐瑶完成 8.5/10，闵娟完成 3/6，整体约 22/27（83%）。核心业务链路、四端页面、亮点技术与文档体系均已交付；未完成部分集中在限流、压测报告、一键化部署、回归验证与版本标签。

### 8.2 项目亮点

1. 三重防护实现限量菜零超卖，并有数据库条件更新兜底；
2. 跨档口原子拆单与退款全量副作用回滚，保证交易一致性；
3. 校园配送担保交易与 Redisson 抢单锁，业务语义完整；
4. Redis 软依赖降级设计，主流程不依赖缓存；
5. AOP 日志落库 + 站内消息 + 投诉超时升级，形成审计与闭环；
6. AI 助手接入 Function Calling，并具备无 Key 降级能力。

### 8.3 不足

1. 新环境无法一键达到可演示状态，补丁依赖人工执行；
2. 演示数据不足以覆盖评价、投诉、消息、日志、二维码核销等场景；
3. 存在严重级别的资损与越权漏洞，尚未修复；
4. 缺乏自动化测试与压测证据，质量保障依赖手工验证；
5. 部分计划任务（限流、压测报告、版本标签）被放弃。

### 8.4 后续改进计划

| 优先级 | 改进项 |
|---|---|
| 1 | 修复批量下单数量校验、JWT 账号状态校验、投诉退款原子性 |
| 2 | 将三个补丁合并进基础 SQL 与 Docker 初始化，实现真正一键部署 |
| 3 | 二维码改为后端签发与验签；统一跑腿费结算与冲正逻辑 |
| 4 | 补充覆盖各状态的演示数据（自取完成单、评价、三态投诉、消息与日志） |
| 5 | 增加后端集成测试与前端构建检查，产出防超卖压测报告 |
| 6 | 补齐管理端送达按钮，修正日志筛选值，处理堂食占位页，创建 v1.0 标签 |
