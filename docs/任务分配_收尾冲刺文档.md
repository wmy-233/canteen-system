## 二、【新增专项】骑手管理功能（组长拍板新增，全员须知）

### 2.1 功能定义
系统在"到店自取（取餐码）"之外，**新增跑腿配送能力，骑手由管理员统一管理**：

1. **骑手档案管理**：管理员录入骑手账号（默认绑定 `RIDER` 角色）、姓名、手机号、在岗/停用状态；可停用（停用后不能再接单）。
2. **配送单流转**：订单新增"配送"类型 → 待分配配送单出现在管理员端 → 管理员指派给某位在岗骑手 → 骑手送达后由管理员/系统将其订单状态置"已送达"。
3. 配送不影响现有取餐码核销流程：**自取单照旧走商家核销，配送单走骑手流转，两条线互不干扰**。

### 2.2 技术落地方案（按此做，不要自行发挥）
| 项 | 内容 |
|---|---|
| 表结构 | `sql/schema.sql` 新增 `rider` 表（`id` / `user_id` / `name` / `phone` / `status` 0停用 1在岗 / `create_time`）；`order_info` 表新增 3 列：`delivery_type` TINYINT 0自取 1配送（默认 0 不影响存量单）、`rider_id` BIGINT 可空、`delivery_status` TINYINT 0未分配 1配送中 2已送达 |
| 角色/权限 | `role` 表增加 `RIDER` 骑手角色；`menu`/`role_menu` 增加权限点 `rider:list`、`rider:manage`，仅授给 ADMIN；后端 `SecurityConfig` 按现有 `/api/admin/**` → ADMIN 规则覆盖骑手接口，**骑手接口全部挂在 `/api/admin/rider/**` 下**，骑手本人不需要登录端 |
| 后端接口 | ① 骑手分页/搜索列表 ② 新增骑手（自动建账号+绑 RIDER 角色）③ 编辑/停用启用 ④ 待分配配送单列表（`delivery_type=1 AND delivery_status=0`）⑤ 指派骑手（校验骑手在岗，`delivery_status 0→1`）⑥ 标记送达（`1→2` 状态机校验，禁止跳变） |
| 前端 | 管理端新增"骑手管理"菜单页：骑手档案表格（分页/搜索/停用启用）＋ "待分配配送单"页签（指派/送达按钮） |

### 2.3 依赖顺序（这条链不许乱）
```
C：schema.sql + init_data.sql 修改（rider 表/新列/RIDER 角色数据/演示骑手）   ← 第 1 步，最先做
    ↓ 之后 A 才能写接口；之后 B 才能写页面
A：/api/admin/rider/** 全套接口 + order_info 三列融入下单流程                ← 第 2 步
    ↓ 之后 B 联调
B：管理端"骑手管理"页面 + 学生下单时可选"自取/配送"（配送单不出取餐码核销线） ← 第 3 步
```

### 2.4 本专项注意点（重要程度★★★）
1. **SRS 第 10 节"范围边界"中原有"骑手/配送模块不做"一行，必须删改**，并把骑手功能补进第 4/5/9 节（C 负责，随 PR 提交；不修订文档答辩时会产生口径矛盾）。
2. `order_info` 加列用 `ALTER TABLE ... ADD COLUMN`，保持 `delivery_type` 有默认值 0，**存量演示数据不允许被破坏**；schema.sql 与 init_data.sql 变更必须同步且群里喊一声（组规）。
3. 指派/送达是**状态机**，接口要做合法性校验（0→1→2，不可逆、不可跳级），非法流转返回业务错误码，不要懒得校验直接 UPDATE。
4. 下单是配送单时同样走钱包扣款+事务，**不能因为加了配送就破坏原有事务一致性**。
5. 骑手演示数据：init_data.sql 预置 2 个骑手账号（1 在岗 1 停用），答辩演示指派流程要用。

## 三、【重点】三端前端界面外观区分规范（组员 B 必读 ★★★）

### 3.1 现状问题
三个角色现在**共用同一个 `FrameLayout.vue`**，除菜单文字外完全一致，答辩时会被质疑"三端没有隔离感"。本条是 B 的**第一优先任务**。

### 3.2 区分要求（三项都要做，验收按此逐条检查）
| 端 | 主色调（Element Plus 主题变量） | 布局差异 | 内容/组件风格差异 |
|---|---|---|---|
| 学生端 `/student` | **橙色系**（主色建议 `#FA541C` / 鼠尾草绿可保留为参考底，最终以橙暖色为准） | 顶栏 + 侧栏均营造"点餐 App"轻松感；菜品用**图片卡片网格**（2~3 列），显著展示价格、余量、销量标 | 圆角大卡片、大字号价格、购物车悬浮明细条、情绪化文案 |
| 商家端 `/merchant` | **蓝色系**（主色 `#1677FF`，侧栏深色 `#001529`） | 经典后台管理风：深色侧栏 + 白色内容区 + 面包屑 | 以**表格为主**（菜品管理、出餐看板队列），紧凑行高，操作按钮小而密，突出核销类大按钮 |
| 管理端 `/admin` | **深色科技风/紫色系**（主色 `#722ED1` 或者深蓝紫大屏风） | 顶部通栏统计卡片区（全局订单量/GMV/用户数）+ 图表区，偏数据大屏 | ECharts 图占比高、卡片式统计、表格浅色描边风格 |

### 3.3 实现建议（避免 B 三处重复劳动）
- 推荐方案：保留 `FrameLayout.vue` 作为壳，加 `theme` prop（`student|merchant|admin`），内部按 prop 切换 CSS class（`:class="\`theme-${theme}\`"`）注入主色变量，菜单样式/顶栏配色随之切换；三端差异靠 **class 主题变量 + 布局插槽**实现，而不是复制三份 layout 文件（复制三份以后改动要同步三遍，禁止那么干）。
- Element Plus 主色通过 CSS 变量覆盖（`--el-color-primary` 系列变量）实现，不改组件库源码。
- 三端顶栏 title 与 logo 文案也要区分：如学生端「校园食光·点餐」、商家端「档口掌柜后台」、管理端「食堂运营数据中心」。

### 3.4 验收标准
- [ ] 三个角色登录后截三张图放一起，**不写说明也能一眼看出是三个不同系统**；
- [ ] 主色互不相同、布局结构至少有一处明显差异（大屏风/表格风/卡片风）；
- [ ] 改主题不影响已有路由守卫与 401 逻辑（回归 `router/index.js` 现有行为）。

## 六、全组统一注意事项（再强调一遍，都是踩过的坑）

1. **Git 规矩**：禁直接 push main；一律 feature 分支 + PR；commit 前缀 `feat:`/`fix:`/`docs:`/`sql:`；每天开工 `git pull` 先行。
2. **数据库变更红线**：表结构一动，`sql/schema.sql` 必须同步改，群里有声，否则别人本地库与你炸库表现象不一致，一律自己背锅。
3. **Redis 降级红线**：所有用到 Redis 的功能（防超卖/热销榜/限流/骑手状态缓存如果有）**必须考虑 Redis 挂掉的行为**——主流程不许死，参考 `RedisSupport` 现有写法。
4. **金额与快照**：钱一律 `DECIMAL`/`BigDecimal`；订单明细存菜名+价格快照——这两条在验收时会被逐条查。
5. **状态机思维**：订单状态、配送状态、券状态全部要在 Service 层做流转合法性校验，禁止 Controller 直接 UPDATE 了事。
6. **权限双保险**：URL 级已配好（`/api/admin/**`→ADMIN、`/api/merchant/**`→MERCHANT），方法级 `@PreAuthorize` 记得补；商家类接口的**数据权限（本档口隔离）靠自己手动校验**，Security 不会帮你做。
7. **答辩三板斧**：防超卖、RBAC、取餐码原理每个负责人脱稿能讲；骑手模块分工与实现过程也要能说清一句。
8. **验收口径**：M2 检查单（浏览/购物车/下单/取餐码全通）、M3（钱包/券/评价/审核全通）、M4（限流/热销榜/报表/文档定稿）逐条勾；三端截图加骑手演示进答辩 PPT。
